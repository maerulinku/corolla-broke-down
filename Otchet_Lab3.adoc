== Цель работы

Продолжить рефакторинг программы управления светодиодами: выделить режим работы в
самостоятельную сущность (интерфейс `IMode` + классы-режимы), собрать режимы в массив и
переключать их автоматически по времени. В результате главный цикл программы должен занимать
несколько строк, а добавление нового светодиода или нового режима — не требовать правки
`main()`.

== Что было сделано на предыдущем этапе

На прошлой лекции «лапшекод» (последовательные `GPIOC::ODR::ODR5::High::Set()` на каждый
светодиод) был заменён на классы с интерфейсами:

* `IPin` / `Pin` — «ножка» порта: установить в единицу, сбросить, переключить, получить
  состояние;
* `ILed` / `Led` — светодиод, который принимает в конструктор `IPin&` и делегирует ему
  вызовы;
* массив `std::array<IPin*, N>` и один цикл `for (auto pin : pins) pin->Toggle();`.

В результате логика управления светодиодами сократилась до 2–3 строк. Использовался
`std::array` вместо обычного C-массива: у него известен размер на этапе компиляции, он не
превращается в «голый указатель» при передаче и не позволяет выйти за границы массива.

== Постановка задачи

Программа должна сама переключать режимы работы светодиодов:

[cols="1,2",options="header"]
|=====================
|Режим |Что делает
|*ModeBlink* |все светодиоды включаются одновременно и одновременно выключаются
|*ModeTree* (ёлочка) |светодиоды по очереди зажигаются, «бегущий огонь»
|*ModeChess* (шахматка) |загораются чётные светодиоды, затем нечётные
|=====================

Режимы переключаются автоматически через условный интервал времени. Слово *условный* здесь
принципиально: точных секунд без таймера не будет, потому что `delay()` — это пустой цикл,
длительность которого зависит от тактовой частоты и оптимизации компилятора. Расчёт интервала
через частоту приведён в разделе <<timing>>.

== Теоретическая часть

=== Интерфейс (контракт)

Интерфейс — это абстрактный класс с чисто виртуальными функциями. Он описывает, *что*
умеет сущность, но не содержит реализации. Класс, наследующий интерфейс, обязан
переопределить все его методы.

[NOTE]
====
Если по указателю на базовый интерфейс предполагается удалять объект, деструктор интерфейса
обязан быть виртуальным (`virtual ~IPin() = default;`). Иначе при `delete` через указатель на
интерфейс вызовется только деструктор базового класса, и поведение программы будет
неопределённым.
====

=== Полиморфизм

`IMode` позволяет обращаться ко всем режимам одинаково: у каждого есть `Init()` и `Work()`.
Хранение режимов в массиве указателей на базовый интерфейс `std::array<IMode*, N>` позволяет
вызывать метод того режима, на который в данный момент указывает индекс, без `if`/`switch`
и без знания конкретного класса.

=== Роль методов Init() и Work()

* `Init()` — приводит режим в начальное состояние. Вызывается как перед первым запуском
  программы, так и при каждом переключении на новый режим. Без этого следующий запуск режима
  начинается не с начала (например, ёлочка «пропускает» первые светодиоды после переключения).
* `Work()` — выполняет один шаг работы режима. Время между шагами задаётся задержкой в
  главном цикле.

Пара «интерфейс + несколько реализаций» — это, по сути, паттерн *Стратегия*: алгоритм
(режим) подменяется во время работы программы.

=== Интерфейс IPin

В интерфейс добавлен виртуальный деструктор — без него удаление объекта через указатель на

[source,cpp]

#define UNTITLED2_CONTRACTS_IPIN_H

class IPin
{
public:
    virtual ~IPin() = default;

    virtual void Set() = 0;
    virtual void Reset() = 0;
    virtual void Toggle() = 0;
    virtual bool GetState() const = 0;
};

#endif // UNTITLED2_CONTRACTS_IPIN_H
----

=== Реализация Pin

В регистре `ODR` нет готового метода «сбросить бит», поэтому сброс выполняется через
чтение текущего значения, обнуление нужного бита маской и запись обратно:

[source,cpp]
----
template <typename TPort, int pinNum>
class Pin final : public IPin
{
public:
    void Set() override
    {
        TPort::Set(uint8_t(1U) << pinNum);
    }

    void Reset() override
    {
        // Считали регистр, обнулили бит pinNum, записали обратно
        TPort::Write(TPort::Get() & ~(uint8_t(1U) << pinNum));
    }

    void Toggle() override
    {
        TPort::Toggle(uint8_t(1U) << pinNum);
    }

    bool GetState() const override
    {
        return (TPort::Get() & (uint8_t(1U) << pinNum)) != 0U;
    }
};
----

Запись `1U << pinNum` — это сдвиг единицы в нужный разряд: для пина 5 получается `0b0010'0000`,
то есть единица в пятом бите. `Set` выставляет этот бит, `Reset` — сбрасывает, `Toggle`
инвертирует.

=== Режим ModeBlink (моргание всеми светодиодами)

Класс принимает массив светодиодов и в `Work()` переключает их все сразу. Начальное состояние —
все светодиоды погашены:

[source,cpp]
----
template <std::size_t Size>
class ModeBlink final : public IMode
{
public:
    explicit ModeBlink(const std::array<ILed*, Size>& leds)
        : leds(leds)
    {
    }

    void Init() override
    {
        for (ILed* led : leds)
        {
            led->PutOut();
        }
    }

    void Work() override
    {
        for (auto led : leds)
        {
            led->Toggle();
        }
    }

private:
    const std::array<ILed*, Size>& leds;
};
----

=== Режим ModeTree (ёлочка)

Здесь `Work()` делает один шаг: переключает светодиод с номером `step`, после чего
увеличивает `step`. Когда номер дошёл до конца массива, он сбрасывается в ноль — так
получается «бегущий огонь»:

[source,cpp]
----
template <std::size_t Size>
class ModeTree final : public IMode
{
public:
    explicit ModeTree(const std::array<ILed*, Size>& leds)
        : leds(leds)
        , step(0U)
    {
    }

    void Init() override
    {
        for (auto led : leds)
        {
            led->PutOut();
        }
        step = 0U;
    }

    void Work() override
    {
        if (step == Size)
        {
            step = 0U;
        }
        leds[step]->Toggle();
        ++step;
    }

private:
    const std::array<ILed*, Size>& leds;
    std::size_t step;
};
----

=== Режим ModeChess (шахматка)

В шахматном режиме светодиоды делятся на две группы по чётности индекса: сначала горят
светодиоды с чётными индексами, затем — с нечётными. Номер группы хранится в поле `phase`
и переключается на каждом шаге:

[source,cpp]
----
template <std::size_t Size>
class ModeChess final : public IMode
{
public:
    explicit ModeChess(const std::array<ILed*, Size>& leds)
        : leds(leds)
        , phase(0U)
    {
    }

    void Init() override
    {
        for (auto led : leds)
        {
            led->PutOut();
        }
        phase = 0U;
    }

    void Work() override
    {
        for (std::size_t i = 0U; i < Size; ++i)
        {
            if ((i % 2U) == phase)
            {
                leds[i]->Light();
            }
            else
            {
                leds[i]->PutOut();
            }
        }
        phase = (phase + 1U) % 2U;
    }

private:
    const std::array<ILed*, Size>& leds;
    std::size_t phase;
};
----

=== main.cpp

Параметры задержки вынесены в именованные константы, чтобы у каждой величины было понятное
название и её можно было пересчитать. Инициализация первого режима выполняется до входа в
цикл, а число шагов режима больше не зависит от количества светодиодов:

[source,cpp]
----
#include <array>
#include "rccregisters.hpp"     // for RCC
#include "gpioaregisters.hpp"   // for GPIOA
#include "gpiocregisters.hpp"   // for GPIOC
#include "Pin.h"                // for Pin
#include "Led.h"                // for Led
#include "ModeBlink.h"          // for ModeBlink
#include "ModeTree.h"           // for ModeTree
#include "ModeChess.h"          // for ModeChess

// --- Параметры тактирования и задержки ---------------------------------
constexpr std::uint32_t CPU_FREQUENCY_HZ = 16000000U; // HSI 16 МГц (задаётся в __low_level_init)
constexpr std::uint32_t CYCLES_PER_LOOP  = 4U;        // оценка: ~4 такта на итерацию delay()
constexpr std::uint32_t STEP_TIME_MS     = 100U;      // длительность одного шага режима, мс
constexpr std::uint32_t MODE_TIME_MS     = 10000U;    // длительность работы режима, мс

// Число итераций пустого цикла на один шаг задержки
constexpr std::uint32_t DELAY_CYCLES =
    CPU_FREQUENCY_HZ / 1000U * STEP_TIME_MS / CYCLES_PER_LOOP;

// Число шагов Work() на один режим
constexpr std::uint32_t DELAYS_PER_10S = MODE_TIME_MS / STEP_TIME_MS;
// ----------------------------------------------------------------------

Pin<GPIOC::ODR,5> pin5;
Pin<GPIOC::ODR,8> pin8;
Pin<GPIOC::ODR,9> pin9;
Pin<GPIOA::ODR,5> pin5a;

Led led1(pin5);
Led led2(pin8);
Led led3(pin9);
Led led4(pin5a);

constexpr std::uint32_t ledsCount = 4U;
std::array<ILed*, ledsCount> leds = {&led1, &led2, &led3, &led4};

ModeBlink<ledsCount> modeBlink(leds);
ModeTree<ledsCount>  modeTree(leds);
ModeChess<ledsCount> modeChess(leds);

constexpr std::uint32_t modesCount = 3U;
std::array<IMode*, modesCount> modes = {&modeBlink, &modeTree, &modeChess};

int main(void)
{
  RCC::AHB1ENR::GPIOAEN::Enable::Set();
  RCC::AHB1ENR::GPIOCEN::Enable::Set();

  GPIOA::MODER::MODER5::Output::Set();
  GPIOC::MODER::MODER5::Output::Set();
  GPIOC::MODER::MODER8::Output::Set();
  GPIOC::MODER::MODER9::Output::Set();

  std::uint32_t modeNumber = 0U;

  // Инициализируем режим, с которого начинаем работу,
  // а не полагаемся на то, что регистры ODR после сброса нулевые
  modes[modeNumber]->Init();

  while (1)
  {
    // Каждый режим делает фиксированное число шагов,
    // независимо от количества светодиодов
    for (std::uint32_t i = 0U; i < DELAYS_PER_10S; ++i)
    {
      modes[modeNumber]->Work();
      delay(DELAY_CYCLES);
    }

    modeNumber = (modeNumber + 1U) % modesCount;
    modes[modeNumber]->Init();
  }
}
----

[[timing]]
== Переключение режимов и расчёт времени

=== Почему число шагов не зависит от количества светодиодов

Работе режима отводится ровно `DELAYS_PER_10S` шагов. Внутри шага `Work()` выполняется один
раз, а задержка — одна и та же. Поэтому добавление или удаление светодиода не сдвигает
тайминг: меняется только «плотность» шагов внутри режима (сколько светодиодов успевает
переключиться за отведённое время), но не длительность режима.

Раньше было наоборот: число шагов считалось как `DELAYS_PER_10S / ledsCount`, и добавление
четвёртого светодиода автоматически сокращало интервал в 4/3 раза.

=== Расчёт длительности шага и режима

`delay(n)` — это пустой цикл на `n` итераций. Одна итерация цикла на Cortex-M4 с
оптимизацией занимает примерно `CYCLES_PER_LOOP = 4` такта (сравнение, инкремент, переход).

[source]
----
T_шага   ≈ CYCLES_PER_LOOP * DELAY_CYCLES / CPU_FREQUENCY_HZ
T_режима  = DELAYS_PER_10S * T_шага
----

Подставляем значения из кода:

[cols="2,1",options="header"]
|=====================
|Величина |Значение
|`CPU_FREQUENCY_HZ` |16 000 000 Гц (HSI)
|`CYCLES_PER_LOOP` |4 такта
|`STEP_TIME_MS` |100 мс
|`DELAY_CYCLES` |= 16 000 000 / 1000 * 100 / 4 = 400 000 итераций
|`DELAYS_PER_10S` |= 10 000 / 100 = 100 шагов
|T_шага |= 4 * 400 000 / 16 000 000 = 0,1 с
|T_режима |= 100 * 0,1 = 10 с
|=====================

[NOTE]
====
Расчёт оценочный: `CYCLES_PER_LOOP` — приближение, компилятор может развернуть или изменить
цикл, а `delay()` не является таймером. Поэтому 10 секунд — *условная* величина (порядка
десяти секунд), а не гарантированные 10,000 с. Для точного интервала нужен системный таймер
(SysTick), что планируется на следующем этапе.
====

=== Переключение

Строка

[source,cpp]
----
modeNumber = (modeNumber + 1U) % modesCount;
----

переводит номер на следующий режим, а `modes[modeNumber]->Init();` приводит новый режим в
начальное состояние. Деление по модулю `modesCount` (вместо жёстко прописанного числа)
позволяет менять количество режимов в одном месте — в константе `modesCount`.

При добавлении четвёртого светодиода меняется только объявление и массив `leds`, а весь

== Выводы

В ходе работы код программы был переведён на архитектуру с интерфейсами и динамическим
полиморфизмом: `IPin`/`Pin`, `ILed`/`Led`, `IMode`/`ModeBlink`, `ModeTree`, `ModeChess`.
Режимы собраны в массив `std::array<IMode*, N>` и переключаются автоматически по счётчику,
а их начальное состояние задаётся методом `Init()`.

Главный результат — *расширяемость*: добавление светодиода сводится к добавлению объекта в
массив, добавление режима — к написанию нового класса и добавлению его в массив режимов,
при этом `main()` остаётся неизменным. Логика работы программы сократилась с десятков строк
до нескольких строк главного цикла, а код стал читаемым и предсказуемым.

Дополнительно закрыты выявленные при ревью риски: реализован рабочий `Reset()` пина (без него
`PutOut()` был заглушкой, а `ModeChess` не мог работать), добавлен виртуальный деструктор в
`IPin`, интервал режима больше не зависит от количества светодиодов и выражен через
именованные константы с расчётом через тактовую частоту.
